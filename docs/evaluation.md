# Evaluation

The gateway makes decisions without a model: OPA policy, regex and checksum redaction, heuristic injection
scoring, and idempotency and audit machinery. The evaluation therefore measures deterministic components
against labelled-by-construction synthetic data, gates every pull request on the results, and is honest
about what synthetic data cannot show. Results live in `evals/REPORT.md`, regenerated by `make eval` from
`evals/reports/*.json`. This page explains how the numbers there are produced and how far to trust them.

## Suites

| Suite | Cases (dev / test) | Metric and gate | Produced by |
|---|---|---|---|
| `policy.v1` | 90 / 60 (`evals/datasets/`) | decision accuracy = 1.0 | `make eval` |
| `injection.v1` | 120 / 80 (`evals/datasets/`) | recall ≥ 0.80, false-positive rate ≤ 0.05 | `make eval` |
| `redaction.v1` | 72 / 48 (`evals/datasets/`) | recall ≥ 0.98, precision ≥ 0.95 | `make eval` |
| `latency.v1` | 10,000 policy evaluations per split | p95 < 1 ms | `make eval` |
| `chaos.v1` | 10,000 calls against the compose stack | duplicates = 0, audited ratio = 1.0 | `make chaos` |

The datasets are generated by `go run ./cmd/datagen` (`datagen.v1`, seed 20260), and each case's label
follows from how it was built:

- **Policy:** each case is a tenant, scopes, tool and arguments drawn around the policy boundaries
  (refund limits, approval holds, missing scopes, tenant allowlists, a `null` arguments listing), with the
  decision the rules prescribe.
- **Injection:** attack templates (instruction overrides, role markers, tool references, exfiltration
  links, obfuscation with hidden Unicode, confusables, base64 and leetspeak) and benign templates
  (ordinary CRM notes and order text) filled with synthetic values.
- **Redaction:** text with test card numbers, checksum-valid IBANs, emails, fictional phone ranges and
  bearer tokens at known offsets, plus look-alikes that must not be touched (Luhn-invalid numbers).

## Method

- **Partitions.** Thresholds and detector rules are tuned on `dev` only. The `test` partition is never
  edited by hand: the `pre_tool_guard.py` hook blocks edits under `evals/datasets/test/`, and the
  `add-eval-case` skill extends the generator instead.
- **Graders** are exact comparisons, so there is no LLM-as-judge and nothing to calibrate. Per-case scores
  are stored in each report, and `scripts/evalgate_check.py` recomputes every metric from them.
- **Confidence intervals** are 95% percentile bootstrap intervals over cases, with 2,000 resamples and
  seed 1337 (`evals/REPORT.md`).
- **The gate** (`make eval`, CI workflow `evals.yml`): each metric must meet its threshold, and any
  regression beyond 1.0 percentage points against `evals/baseline/` fails. Because the graders are
  deterministic, a delta is a real change, not noise. A missing report or metric, or a reported value
  that differs from the recomputed one, also fails (`docs/DECISIONS.md`).
- **Reports** follow the `evalgate.report.v1` schema (`evals/schemas/`), with `mode: offline`,
  `models: []` and `prompt_hashes`: the SHA-256 of the policy bundle and of the detector source files, so
  a report states exactly which rules produced it.
- **Chaos.** `make chaos` sends 10,000 calls (20% retries) through the compose stack while 10% of refund
  keys stall past the gateway timeout. It counts refund rows per idempotency key in Postgres and audit
  events per call, then verifies the chain (`evals/reports/chaos.v1.json`).
- **Live evals.** No model is called, so there is no provider key and no cost. `make eval-live` prints
  the USD 0.00 estimate and reruns the same offline graders; it does not drive the compose stack.
  `evals/REPORT.md` states that live evals were not run.

## Results

The current numbers are in `evals/REPORT.md` and are not copied here, so they cannot drift. Policy
accuracy, redaction recall and precision, injection false positives, chaos duplicates and the audited
ratio are at their gates or better. Injection recall on the test partition sits at its gate, and dev
recall is higher (`evals/REPORT.md`).

## What the numbers do not show

- **Injection scoring is defence in depth, not a solution.** The scorer looks for known shapes of
  prompt injection: override phrases, role markers, hidden Unicode, tool references, imperative density,
  links with query strings and base64 blobs. A determined attacker can write instructions that match
  none of them. The controls that hold regardless of the score are elsewhere: every upstream result is
  marked untrusted, policy limits what any agent may call, writes above limits need a human approval,
  and every call is audited.
- **Template overlap.** Dev and test are split per case, not per template, so test recall measures new
  fills of known phrasings, not new phrasings (`docs/KNOWN_LIMITATIONS.md`). A later `injection.v2`
  should split by template and add out-of-template hard negatives.
- **Synthetic formats.** Redaction cases use a fixed set of formats; real-world recall will be lower,
  and names and street addresses are out of scope for the detectors.
- **Human review.** The labels of 40 injection cases have not yet been reviewed by hand.

## Reproducing

```sh
make eval            # offline suites, gate, evals/REPORT.md
make up && make seed
make chaos           # chaos.v1 against the stack
```
